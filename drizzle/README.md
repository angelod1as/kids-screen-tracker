# Migrations

Generated by `pnpm db:generate` from `src/db/schema.ts`, applied by
`pnpm db:migrate`. The SQL in this folder is committed and reviewed: it, and not
the TypeScript, is what actually runs against the database.

Do not edit a `.sql` file by hand once it has been applied anywhere. The
migrator records a hash of each file in `__drizzle_migrations`, so an edited
file that has already run is simply skipped — the change silently never happens.
Change `src/db/schema.ts` and generate a new migration instead.

## These migrations are not reversible, and that is deliberate

`drizzle-kit generate` emits forward SQL only; there is no `down` file, and none
is written by hand here. Three reasons, in order of weight:

1. **A rollback of a schema change is a rollback of data.** Dropping a column
   destroys what is in it. For a ledger and an activity history whose whole
   purpose is that a three-month-old entry still reads correctly (D15), an
   automated `down` is a loaded gun with no safety.
2. **The recovery procedure here is restoring a backup.** The database is one
   SQLite file on one volume, for four users. Restoring a backup taken before
   the deploy is faster, simpler and more complete than any `down` migration,
   and it is the procedure Phase 7 already owes a command for. Take that backup
   with `VACUUM INTO`, never with `cp` — see below.
3. **Nothing is deleted anyway (D14).** Categories and activities are
   deactivated, never dropped, and every foreign key is `ON DELETE RESTRICT`.
   The destructive migrations that most need a `down` are the ones this schema's
   own rules keep out.

If a migration ever does need undoing, write the reversal as a new forward
migration. It leaves the trail in one direction, which is the property that
makes `__drizzle_migrations` trustworthy.

## Taking a backup: `VACUUM INTO`, never `cp`

```sh
sqlite3 /data/kids.db "vacuum into '/data/backup-$(date +%F).db'"
```

`cp` is wrong, and it is wrong quietly. Connections are opened in WAL
(`src/db/client.ts`), so at any moment part of the committed data lives in
`kids.db-wal` next to the file. Measured, with 40 committed ledger rows and
another connection mid-write:

```
files on the volume       : kids.db, kids.db-shm, kids.db-wal
cp kids.db copy.db
rows in the copy          : 0      <- expected 40
integrity_check           : ok
```

`integrity_check` says `ok`. The copy is a valid SQLite database that is simply
missing everything, which is the worst shape a backup can take. Copying all
three files is not a fix either: they are not copied atomically, so the set can
be internally inconsistent.

`VACUUM INTO` writes one consistent file from inside SQLite, with no downtime.
The same run, with that write transaction still open:

```
rows in the backup        : 40     <- expected 40
integrity_check           : ok
files in the backup       : backup.db
```
